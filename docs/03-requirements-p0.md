# 03. 기능 요구사항 - P0 (PRD 6장)

> 원문: [00-prd-full.md](./00-prd-full.md) · 인덱스: [README.md](./README.md)

## 6.1 사진 선택 및 EXIF 검사

사용자는 사진을 1장 이상 선택할 수 있다. 앱은 다음을 확인한다: GPS 위도, GPS 경도, 촬영일시, 이미지 접근 가능 여부.

| 조건                     | 처리                                                             |
| ------------------------ | ---------------------------------------------------------------- |
| GPS 있음 + 촬영일시 있음 | 자동 관광지 후보 조회 플로우로 이동                              |
| GPS 있음 + 촬영일시 없음 | GPS 기반 후보 조회 후 방문일은 사용자 입력 또는 현재 날짜로 보완 |
| GPS 없음 + 촬영일시 있음 | 관광지 직접 검색 플로우로 이동                                   |
| GPS 없음 + 촬영일시 없음 | 관광지 직접 검색 + 방문일 입력 플로우로 이동                     |
| 이미지 접근 실패         | 사진 선택 실패 안내                                              |

안내 문구 예시:

- “사진의 위치 정보를 확인했어요. 주변 관광지를 찾는 중입니다.”
- “이 사진에는 위치 정보가 없습니다. 관광지를 직접 선택해주세요.”
- “촬영일시를 찾을 수 없습니다. 방문 날짜를 선택해주세요.”

## 6.2 위치정보 처리 원칙

위치정보 처리 범위를 최소화하기 위해 GPS 좌표를 Tripic 백엔드 서버로 전송하거나 로컬 DB에 저장하지 않는다. 다만 후보 조회 시에는 한국관광공사 OpenAPI로 직접 전송되므로 별도 고지·동의와 위치정보법 적용 여부를 검토한다.

- EXIF GPS 좌표는 앱에서 추출하여 후보 조회에 필요한 동안만 처리하고 로컬 DB에 저장하지 않는다.
- 관광지 후보 조회는 앱이 GPS 좌표를 관광공사 OpenAPI로 직접 전송하여 처리한다.
- 백엔드 서버는 GPS 좌표를 수신/저장하지 않는다.
- 사진 원본을 서버에 업로드하지 않는다. 필요 시 EXIF 위치 정보를 제거한 사본만 업로드한다.
- P0에서는 방문 기록을 앱 로컬 저장소에 저장하는 것을 기본으로 한다.
- 서버 동기화가 필요하면 위치정보지원센터 공식 사전 검토 후 범위를 결정한다.

## 6.3 한국관광공사 OpenAPI 활용 원칙

공모전 FAQ 및 가이드에 따라 OpenAPI 데이터를 로컬/서버 DB에 저장·캐싱 서빙하지 않는다.

- 관광지 후보 조회는 실시간 호출한다.
- 상세 정보는 화면 표시 시점에 호출하여 조회한다.
- 관광지명·주소·소개·대표 이미지·지역/분류 등 원천 데이터는 저장하지 않는다.
- 사용자 기록에는 contentId와 사용자 확정 기록 정보만 저장한다.
- 실제 사용자 플로우에서 호출 이력이 남도록 한다.
- API 인증키 관리 방식은 별도 기술 검토 필요.

| OpenAPI             | P0 활용                             |
| ------------------- | ----------------------------------- |
| 위치 기반 관광정보  | GPS 좌표 기준 주변 관광지 후보 조회 |
| 키워드 검색         | GPS 없는 사진의 관광지 직접 검색    |
| 공통정보 조회       | 관광지명·주소·소개 등 상세 표시     |
| 이미지정보 조회     | 기록 카드 대표 이미지 표시          |
| 지역코드 / 분류코드 | 지도 스탬프 및 관광 유형 표시       |

## 6.4 관광지 후보 조회

위치 기반 관광정보 OpenAPI 호출. 기본 조회 기준:

- 기본 반경 300m → 후보 없으면 1km까지 확장 → 1km 내 없으면 직접 검색 플로우로 이동
- 후보 최대 노출 5개, 기본 정렬 거리순

후보 목록 표시: 관광지명, 주소, 거리, 관광 유형, 대표 이미지, 지역명. (저장하지 않고 화면 표시용으로만 사용)

| 신뢰도    | 기준                           |
| --------- | ------------------------------ |
| 높음      | 100m 이내 단일 후보            |
| 보통      | 300m 이내 복수 후보            |
| 낮음      | 300m 초과 1km 이내 후보        |
| 수동 필요 | GPS 없음 또는 1km 내 후보 없음 |

P0에서는 자동 확정하지 않고 사용자가 최종 방문지를 확인/선택한다.

## 6.5 방문지 확정

사용자 행동: 후보 선택 / 관광지명 검색 / 지역 기준 검색 / “해당 없음” 후 재검색.

확정 시 로컬 저장 데이터: 로컬 기록 ID, 사진 로컬 참조, contentId, 방문일시, 지역코드, 시군구코드(선택), 관광 유형 코드(선택), 매칭 방식, 매칭 신뢰도, 사용자 확정 여부, 생성일시.

매칭 방식 값: `GPS_CANDIDATE`, `MANUAL_SEARCH`, `MANUAL_REGION_SELECT`.

contentId와 사용자 기록만 저장하고 관광공사 원천 데이터 전체는 저장하지 않는다.

## 6.6 여행 기록 카드 생성

필수 표시: 사용자 사진, 관광지명, 주소, 방문일시, 지역, 관광 유형, 대표 이미지, 관광지 간단 소개. (관광지명/주소/소개/이미지는 로컬 저장이 아니라 표시 시점에 OpenAPI 호출로 조회)

생성 흐름: ① 사용자 확정 → ② contentId 로컬 저장 → ③ 카드 진입 시 공통정보/이미지정보 OpenAPI 호출 → ④ 응답과 사용자 사진 결합하여 표시. 카드 생성은 AI 해설에 의존하지 않는다.

## 6.7 방문 기록 Flow

**생성**: 사진 선택 → EXIF 확인 → GPS를 Tripic 서버나 로컬 DB에 저장하지 않음 → GPS를 OpenAPI로 직접 전송해 후보 조회 → 사용자 방문지 선택 → contentId+방문일시로 로컬 기록 생성 → contentId로 OpenAPI 호출하여 상세 표시 → 지도 스탬프 반영.

**조회**: 기존 기록 열기 → 로컬에서 contentId·방문일시·사진 참조 조회 → contentId로 OpenAPI 호출 → 상세 수신 → 로컬 사진과 조합 표시 → 실패 시 오류 안내+재시도.

**수정**(최소): 방문일시, 연결 contentId, 사용자 메모(선택). 관광지 변경 시 키워드/주변 재검색 → 새 contentId로 교체 → 지도 스탬프 재계산.

**삭제**: 삭제 선택 → 확인 안내 → 로컬 기록 삭제 → 사진 참조 제거 → 지도 스탬프 재계산 → 복구 없음.

## 6.8 지도 스탬프

P0 기능: 시·도 단위 방문 표시, 방문 지역 수, 전체 지역 대비 진행률, 최근 방문 기록 3개.

표시 예시: 방문 지역 3/17 · 기록한 관광지 8곳 · 최근 기록(경복궁, 남산서울타워, 해운대해수욕장).

갱신 Flow: 기록 생성/수정/삭제 시마다 로컬 기록 기준 지역별 방문 수 재계산 → areaCode 기준 시·도 방문 여부 판단 → 1개 이상이면 방문 완료, 0개면 미방문으로 복귀. 시·군·구 상세 달성률·유형별 달성률·뱃지/칭호는 P0 필수 아님.

## 6.9 AI 해설

P0 필수 아님. P1 선택 구현 시: AI 한 줄 해설만, 카드 생성 이후 수동/비동기 생성, 실패가 카드 생성 실패로 이어지지 않음, OpenAPI 조회 정보 근거로만 생성. AI 여행 일기·대화형 컨시어지·추천 미션은 P1 기본 범위 제외.

## 6.10 이미지 유사도 분석

P0 제외. 사유: 관광공사 이미지 수집·임베딩 저장 시 정책 이슈, 유사도만으로 확정 시 정확도 리스크, P0 핵심은 GPS 기반 실시간 호출+사용자 확정. P1 이후 정책 확인 후 후보 정렬 보조로만 검토.
