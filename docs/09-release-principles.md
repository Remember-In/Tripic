# 09. 릴리스 계획 · 완료 기준 · 설계 원칙 · 기술 의사결정 (PRD 18~21장)

## 18. 릴리스 계획

### M1 — P0 핵심 기록 루프

사진 위치 기반 후보 조회와 기록 카드 생성 검증. 사진 선택, EXIF 검사, OpenAPI 직접 호출, 후보 표시, 방문지 확정, 카드 생성, 로컬 저장, 지도 스탬프, 기록 삭제, NestJS health/app-config API.

### M2 — P0 안정화

실패 케이스·UX 완성도. GPS 없는 사진 직접 검색, OpenAPI 실패/지연 대응, 촬영일시 없는 사진 보완, 지도 화면 개선, 카드 상세 개선, 개인정보/위치정보 안내 강화, NestJS 공지/약관/버전 체크 API.

### M3 — P1 확장

기록 지속 사용 동기 강화. 기록 목록, 기록 수정, 사용자 메모, 간단한 뱃지/칭호, 미방문 지역 표시, AI 한 줄 해설(선택).

### M4 — P1 이후 검토

수상작 미션, 다음 여행지 추천, 이미지 유사도 후보 정렬, 공유/내보내기, 서버 동기화, 계정 로그인, PostgreSQL/Prisma 도입. 이미지 유사도·서버 동기화·관광공사 데이터 가공 저장은 운영 측/위치정보지원센터 사전 검토 후 진행.

## 19. P0 완료 기준

- 여행 사진 선택 가능
- EXIF GPS·촬영일시 확인 가능
- GPS 좌표 Tripic 서버·로컬 DB 미저장 및 TourAPI 직접 전송 고지
- GPS 기준 OpenAPI 실시간 호출 가능
- 주변 관광지 후보 표시 가능
- 후보 선택 또는 직접 검색 가능
- 확정 관광지로 기록 카드 생성
- 카드에 사용자 사진 + OpenAPI 조회 관광지 정보 표시
- 방문 기록 로컬 저장
- 방문 기록 지도 스탬프 반영
- GPS 없는 사진은 직접 검색 플로우 처리
- OpenAPI 실패 시 재시도/직접 검색 제공
- 개별 기록 삭제 가능
- OpenAPI 데이터 로컬/서버 DB 원천 저장·캐싱 서빙 없음
- NestJS는 비위치성 운영 API만 제공
- 서버 DB/ORM 미사용

## 20. 핵심 설계 원칙 요약

1. OpenAPI는 실제 사용자 플로우에서 실시간 호출.
2. 관광공사 원천 데이터는 로컬/서버 DB에 저장하지 않음.
3. 사용자 GPS 좌표는 Tripic 서버로 전송하거나 로컬 DB에 저장하지 않음.
4. EXIF GPS는 앱에서 한국관광공사 OpenAPI로 직접 전송하는 후보 조회에만 사용하고, 전송 전에 고지·동의 절차를 제공.
5. 방문 기록은 contentId + 사용자 확정 정보 중심 로컬 저장.
6. 관광지를 자동 확정하지 않고 사용자가 최종 확정.
7. P0는 지도 스탬프와 기록 카드 생성에 집중.
8. 서버는 NestJS, 비위치성 운영 기능에 한정.
9. P0는 DB/ORM 미사용.
10. P1은 로컬 기록 기반 뱃지/칭호·기록 UX 개선 우선.
11. AI·이미지 유사도·수상작 미션·서버 동기화는 정책 검토 후 확장.

## 21. 포트폴리오 관점 기술 의사결정 요약

1. 위치정보 리스크 감소를 위해 GPS 서버 전송 제거.
2. OpenAPI 검증 요건에 맞춰 앱에서 실시간 호출 설계.
3. 서버는 NestJS 기반 비위치성 운영 API로 제한.
4. 로컬 기록은 contentId 중심 저장, 상세는 조회 시점 OpenAPI 재호출.
5. TanStack Query로 OpenAPI loading/error/retry lifecycle 관리.
6. Expo SQLite로 서버 DB 없이 로컬 방문 기록 관리.
7. pnpm workspace로 TypeScript 모바일/서버 모노레포 구성.
8. P0는 DB/ORM 제외, P1/P2에서 PostgreSQL/Prisma 도입 가능하도록 확장성 확보.
